# 形式化验证的范围与重放

性能样本基点：8093775。测量日期：2026-11-11。
本记录还包含随后收口的明确拒绝检查。

这里做的是有限状态模型与真实实现的穷举对照，以及独立的连续业务检查。
模型通过不等于整个插件已经得到数学证明，也不代替完整发布验收。
本轮先修正已确认的抽象缺口，再调整测试夹具；没有缩减原生模型的状态或事件。

| 检查 | 当前范围 | 目的 |
| --- | --- | --- |
| 原生单会话模型 | 2,465 个可达状态、56 个事件、138,040 条边 | 核对分区、人工确认、输入提醒、阶段及 pending 关系 |
| 草稿模型 | 30 条边 | 核对首次/重复创建、返回记录、请求及项目/会话身份、明确拒绝 |
| 冻结参考模型 | 40 个状态、13 个事件、520 条代表路径 | 保留独立 Python 参考模型和全部前缀 |
| 两套冻结模型重放 | 每套 1,417 个实际执行步骤、40 次重启、40 次查看 | 分别验证本地 Store 和远端宿主适配器 |
| 连续业务检查 | 不在每步重装夹具 | 核对跨步骤计数、过期请求、输入提醒、重试、归档和持久化 |

旧原生模型只有 1,077 状态、37 事件、39,849 条边。它遗漏了没有确认锚点时的
输入历史，也没有区分 pending 与已确认阶段是否属于同一轮次。这两项都会影响
后续行为，不能仅按当前列或“是否存在阶段”合并。现有 BFS 的完整状态去重保留；
本轮没有采用新的业务状态合并或删边。

`Read(Review) → Input → Read(ToArchive) → Archive` 现在必须保留复核提醒并拒绝归档。
同轮 pending 的重试覆盖全部已确认/待确认阶段组合；重复已确认阶段不能误当成
新的执行，也不能提前吃掉尚未确认的 pending。

原生逐边重放核对返回成功/拒绝、状态版本和输入版本增量。未读分区、人工操作、
归档和草稿只接受明确的业务拒绝原因；SQL、解码等异常必须向上传播。
相同提示文字包装了底层错误也不能算作正常拒绝。运行阶段分别核对无需移动、
业务拒绝和返回待确认请求，不能用不改数据的 `Ok(None)` 冒充后两者。
首次旧阶段建立基线时仍允许无需移动；已确认过阶段后不能沿用这个例外。
重试也单独核对返回类别，防止实现提前提交后返回None，绕过应执行的确认。
独立连续测试从真实发现开始，检查两个版本维度的冲突、重复输入、新输入批次、
同列不同阶段、归档准备的输入依据及确认时的再次校验。连续编辑、归档与未读阶段
拒绝检查比较逻辑 schema 和实际所有业务表的完整类型化数据，不仅比较模型投影。
快照覆盖持久主库；连接内的临时重启标记单独核对。
人工备注在自动流转、归档和恢复之后仍需保留。

草稿保留原有30条模型边；每条非Absent转换后再次Begin同请求，
核对fresh、返回记录、持久记录与待核对索引。这样也覆盖绑定会话后放弃、
随后重试同请求的历史，避免只用无会话ID的Abandoned夹具漏掉身份丢失。

时间检查分别验证首次观察时间的 `<、==、>`，以及完成/失败/中断的完成时间相对
人工选择的 `<、==、>`；开始与完成时间刻意不同。同轮 pending 需要分别绕过首次
历史保护和旧终态保护。真实重启接管并关闭 Store，再打开同一临时磁盘目录；
用连接内临时表确认新连接没有复用旧连接，再比较持久数据与标题启用时间，
然后继续重试、归档和恢复。它覆盖正常关闭重开，
没有模拟断电或异常进程终止。

状态图里的 `Input` 表示含新用户项的快照，不枚举任意空历史替换。后续空历史不能
清掉已有复核提醒，由独立连续测试核对。图内不变量不能用于删除真实库中的图外
记录。版本在单边夹具中归一到固定基线，多步计数另验；这不是全部整数取值、
任意字符串、任意时钟偏差或并发交错的证明。分区标识也经过归一化，真实配置、
原生分区识别、RPC 接线和跨主机行为仍依赖对应模型与集成检查。

原生重放继续使用逐边 SQL 安装。夹具清理在一个事务中覆盖六张业务表，避免前一条边的审计记录、
设置或远端缓存残留；合成夹具的 `seen_at` 固定为 1，便于精确比较。原有 2,465
状态检查保留，并在每个状态安装前污染六表及未投影的会话字段，与独立安装的干净
参考 Store 比较完整快照。

冻结重放在每个测试组内复用一份空 schema。每条路径开始前，旧 Store/Partition
已经销毁；短连接在一个事务里清空六表，提交并关闭，再用新连接检查全空及 schema
不变。随后重新构造 Store，或重新构造 Partition 和 Surface，并执行原来的发现、
历史读取、初始运行和全部路径前缀。settings 也清空，标题启用时间由新 Store 产生。
每条远端路径重新产生 timestamp 和 base；路径中的 restart 保留它们和 Surface。

schema 基准只在本组首次正常构造后取得。新增表、索引或 trigger 导致检查失败，
不能用重新采样基准掩盖变化。查看和重启的完整快照比较放在公共状态断言之后，
因此也覆盖断言本身调用的读操作。远端另外检查 Surface 全值和 generation。
计数在步骤执行和断言通过之后增加，没有用输入数组长度代替实际执行数。
业务事务、磁盘重启和 SQLite 同步设置保持原有执行方式。

2026-11-11 的本机调试构建测量不含编译。两套冻结重放按单测试、单测试线程顺序
运行，参考模型/需求/锁的内容相同。旧提交钩子产物内嵌的临时源码路径已经清理，
比较时只为它们恢复了经逐字节核对的冻结验收输入；旧二进制仅用于性能基准。

| 测量 | 原方式 | 调整后 |
| --- | ---: | ---: |
| 原生 138,040 边 SQL 重放 | 35.047 秒 | 37.339 秒 |
| 本地冻结模型 520 条代表路径 | 170.418 秒 | 76.530 秒 |
| 远端冻结模型 520 条代表路径 | 207.598 秒 | 96.591 秒 |

原生清理补全后成本略增，保留这项隔离保证；两套磁盘重放减少了重复建库。
原生最终计时包含完整六表清理，冻结重放最终计时包含新增的连接标记检查。

SQLite Backup 候选通过了全初态快照等价及污染隔离实验，但没有采用。同一编译单元、
同一组 256 状态/14,336 边，按 SQL、Backup、Backup、SQL 顺序测得
3.719、4.137、4.115、3.670 秒；复制在这组测量中更慢。上述时间属于本机样本，
会随磁盘和其他任务负载变化，不能当作稳定时限或通用倍数保证。

39 个生产行为单点变异被实际测试捕获，原实现对照通过。具体变化与捕获点见
`context/results/formal-mutations-20261111.md`；编译失败没有计为捕获。
另外核对了 11 个验证设施错误：分别漏清六表、未提交清理、忽略 schema 变化，
以及本地、远端和原生连续测试中的三种伪重启。远端即使把 generation 重置为零，
仍然复用旧连接也会被连接标记捕获。

```bash
cargo test --test board_contract --locked --offline state_contract_tests:: -- --test-threads=1
cargo test --example remote_parity_lab --locked --offline model_replay_tests:: -- --test-threads=1
python3 scripts/verify_acceptance.py --report /tmp/formal-acceptance.json

```

冻结的 31 条需求、参考模型和锁保持原样。完整验收仍要求当前实现对应的外部证据；
自动检查通过但缺证时应保留待验证状态，不能把 `release_ready=false` 写成发布完成。
