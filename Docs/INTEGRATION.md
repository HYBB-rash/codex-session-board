# 提交、PR、集成候选与发布

2026-11-14 起，按用户明确授权执行分层规则。
历史提交继续按自身记录的版本规则检查，不改写历史。

## 开发提交

保留最多 13 文件、400 行的改动规模限制。
提交钩子检查实际暂存快照、注释、清单、版本和检查设置，不要求整项功能可交付。
Clippy、业务测试和检查工具自测不在每个提交重复执行。
普通提交保持现有版本；`--prepare-commit` 在新规则下不会增加版本。

## PR

一个 PR 说明一个明确目的、改动范围、相关验证及依赖。
代码审阅包含业务变化、测试绑定和数据保护。
开发者只更新本任务记录，不竞争修改版本清单或共享状态。
原始小提交保留，不由协调者逐个重放。

## 集成候选

固定主线和原 PR 头，使用隔离工作树集中整合。
合并时分别审核带入的开发提交和手工冲突修改，不能以提交标题取得豁免。
完整门禁绑定最终源码和提交身份；缺失、跳过或失败不能视为成功。
候选改变后，之前的通过记录不替新候选签收。
有依赖的 PR 一起处理；独立失败项可以移出，重新验证剩余组合。
主线在候选完成后若前进，重新整合和验证，不强制推送。

## 发布

协调者在完成合并后运行 `./scripts/check --prepare-release`。
该操作记录绑定源码父提交的升版意图，并统一更新四个版本清单。
再次执行不会重复增加版本。
冻结候选后执行组合验证和打包，部署同一不可变产物。
完整 31 条验收及外部证据门槛继续保留，候选自动通过不等于 release_ready。
部署任务如按用户授权携带既有缺证，必须明确记录，不能冒称完整验收完成。
