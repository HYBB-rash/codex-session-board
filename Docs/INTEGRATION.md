# 提交、PR、集成候选与发布

2026-11-14 起，按用户明确授权执行分层规则。
历史提交继续按自身记录的版本规则检查，不改写历史。

验证入口、环境选择、第二版报告与清理约束见 [统一验证说明](VALIDATION.md)。

## 开发提交

保留最多 13 文件、400 行的改动规模限制。
提交钩子检查实际暂存快照、注释、清单、版本和检查设置，不要求整项功能可交付。
Clippy、业务测试和检查工具自测不在每个提交重复执行。
普通提交保持现有版本；`--prepare-commit` 在新规则下不会增加版本。

## PR

一个 PR 说明一个明确目的、改动范围、相关验证及依赖。
代码审阅包含业务变化、测试绑定和数据保护。
开发者只更新本任务记录，不竞争修改版本清单或共享状态。
原始小提交保留，不由协调者逐个重放。
作者交付前运行绑定最终源码的 PR submit 检查，保留业务测试并记录发布风险，
保存失败、原始日志与未执行清单，详见 `Docs/PR-DELIVERY.md`。
完整 PR CI 与候选构建并行，最终头的 PR CI 通过后才能推进主线。

## 集成候选

固定主线和原 PR 头，使用隔离工作树集中整合。
合并时分别审核带入的开发提交和手工冲突修改，不能以提交标题取得豁免。
完整门禁绑定最终源码和提交身份；缺失、跳过或失败不能视为成功。
合并门禁执行项目规则、全目标 Clippy、严格核对清单的业务及组合测试，并预检源码包。
最终组合通过且主线确认同一候选，PR 合并即完成；不等待发布打包、上传或启动检查。
安装、当前客户端加载、真实界面及远端功能验收属于后续独立任务。
候选改变后，之前的通过记录不替新候选签收。
有依赖的 PR 一起处理；独立失败项可以移出，重新验证剩余组合。
主线在候选完成后若前进，重新整合和验证，不强制推送。

## 发布

协调者在冻结最终合并候选时运行 `./scripts/check --prepare-release`。
该操作记录绑定源码父提交的升版意图，并统一更新四个版本清单。
再次执行不会重复增加版本。
冻结后先执行组合门禁；进入 main 后自动构建和发布同一固定源码的不可变产物。
连续合入的多个 PR 可以同属一个发布版本，不要求每个 PR 单独产包。
PR 合并、候选渠道发布、安装、客户端加载及完整验收是独立状态。
完整 31 条验收及外部证据门槛继续保留，候选自动通过不等于 release_ready。
部署任务如按用户授权携带既有缺证，必须明确记录，不能冒称完整验收完成。

## 实际入口

发布前快速检查运行 `./scripts/validate --scope preflight --output /tmp/preflight-result`。
它只打包与解包源码、比对完整实现指纹、版本和入口执行权限，不编译或启动插件。
候选CI也在完整验证前调用此入口。结果不是完整候选门禁，不能用于提升主线。

安装后的独立生效检查运行
`./scripts/verify-plugin --client-pid CLIENT_APP_SERVER_PID --expected-source RELEASE_SOURCE_SHA --config-id EXPECTED_CONFIG_ID --output /tmp/plugin-proof.json`。
默认只读，核对安装与缓存全部文件、实际HTTP服务身份、配置和数据目录、
MCP可执行文件、所选客户端的父子进程关系及检查期间进程身份未变化。
不根据旧安装回执或无关守护进程宣称当前客户端加载成功。
退出0表示已核实，退出2表示已安装但仍待当前客户端加载，退出1表示核验失败。
可选`--reconnect`复用更新工具已有的定向重连；没有受支持的当前桌面连接时仍返回待重连。
入口优先使用已有交付Python环境，缺少重连依赖时记录失败原因，不输出未核实的成功。
不能启动另一个看板进程冒充成功。报告保存配置摘要，未提供`--config-id`时不代签配置内容已加载。

现场冒烟运行
`./scripts/smoke-plugin --receipt /tmp/plugin-proof.json --session-id EXPLICIT_TEST_SESSION_UUID --output /tmp/plugin-smoke`。
它再次调用生效检查，对实际服务页面执行筛选、取消、空白原因、备注清空和真实等待反馈。
仅操作明确指定的本机卡片，逐次核对服务身份与版本，结束后用服务原有版本保护恢复人工状态和备注。
发现并发修改时拒绝覆盖，报告恢复错误；不会回滚数据库、版本或历史记录。
每次写入前保存恢复记录，保留截图和原始错误，核验全部原备注及配置，清理本次独立浏览器。
默认要求关闭标题、分区同步及自动归档；其他模式应在隔离环境安排专门验收。
此入口记录的是实际HTTP页面，不冒充原生插件容器内的指针拖动或完整31条验收。
每次使用新的源码外报告目录。三个CLI均记录实际耗时，原失败材料不覆盖。

开发提交运行 `./scripts/check --pre-commit`；PR 运行
`./scripts/validate --scope pr --stage submit --base origin/main --output /tmp/pr-result`。
协调者将合格的固定 PR 头依次机械合并到 `codex/integration-*` 分支。
冲突、失败及缺少证据的 PR 退回原作者会话，作者修复后由独立审阅者确认，
协调者核对新头对应的证据后重新入队；不在合并任务中接手业务修复。
独立项继续，有依赖的项一起等待。最终组合没有未处理的失败时，
运行 `./scripts/check --prepare-release`，提交后推送候选分支。

候选工作流在 Linux 与 macOS 分别运行组合门禁，保存绑定当前提交和平台的记录，
确认 `Candidate gate` 成功后才可推进 main；不构建或上传发布包。
两端均执行项目检查、全部目标 Clippy，再按固定主线到候选的实际改动选择回归范围。

| 改动 | 实际执行 |
| --- | --- |
| 已知界面文件及其直接回归脚本 | Rust 库、状态契约、存储、插件运行及全部界面回归 |
| 普通 Rust 业务文件、已知原生适配/打包脚本、Python 回归及其混合改动 | 全部 Rust 业务与 Python 回归，排除提交规则工具自测 |
| 新增上述普通文件 | 同样执行应用回归，不因新增而带入无关工具自测 |
| 删除业务文件、模式变化、依赖、工具、工作流或未知路径 | 完整 automated，包括全部工具自测和 Python 验收器自测 |

范围分类只豁免普通上下文记录及经结构比对的候选版本字段；删除、可执行位及符号链接
不能借已知路径进入较小范围。重演来源只能扩大范围，不能缩小实际候选差异。
即使采用较小范围，也先编译并收集完整测试清单，与全部绑定逐项比对。
缺失绑定、结果缺项、跳过、失败和异常退出仍拒绝候选。
报告为独立的 `scope=integration`，逐项保存执行和未执行清单及每组耗时，
要求所有选中项实际通过；未执行项不记为通过，`release_ready=false`。
完整 automated 和完整 31 条验收入口保持原判定，稳定发布仍要求完整证据。
完整回归中只有提交钩子及检查器两组自测同时运行，每组两线程。
库与 native_authority 各自在组内使用两线程；其他业务及性能组仍为一线程。
业务组之间仍按顺序执行，原阈值和失败条件不变，不会失败后自动改为串行放行。

### main 自动发布

`plugin-release.yml` 响应 main push，复用 `./scripts/release`。
协调者推进 main 后也显式 dispatch，覆盖 Actions token 的 push 不再次触发工作流的情况；
dispatch 有界重试，故障不改变已经完成的合并，回执保留 pending、错误和重试命令。
同一发布工作流每十分钟调和一次，补偿遗漏触发；已发布实现直接复用，不重新产包。

工作流共用一个 concurrency group，`cancel-in-progress: false`：
正在运行的固定源码继续完成；最多保留一个等待任务，更新请求替换旧等待任务。
任务取得执行权后只选取一次最新 main，实现提交与版本随后固定，不在构建中途换源码。
GitHub 不保证等待任务顺序，因此不能按触发事件的旧 SHA 发包。
只改普通 context 记录时沿第一父链复用前一个实现提交，包继续标注真实源码；
两平台渠道、不可变 Release 与版本标签已经一致时直接记录 covered，不再构建。

发布入口核对同源码的双平台合并证据，不重复运行 Clippy 或整套业务测试。
本阶段构建 release 二进制和当前源码 fixture，检查包内容、摘要、真实隔离启动、
配置漂移、MCP 错误退出、错误后台零字节、服务提前退出及侧栏归属。
正常启动仅在场景组执行一次，成功记录作为 STARTUP 证据。
平台包、校验和、STARTUP 和 SCENARIOS 保存在同一版本的 draft Release，
读回后才可冻结；缺少任一平台的有效证据不能发布。
重试复用已经验证的不可变资产，不能覆盖同名不同内容。
最终一次原子 Git push 更新两个候选渠道，避免一新一旧；stable 仍需完整外部验收。

```sh
./scripts/release main status --source MAIN_SHA
./scripts/release main dispatch
```

队列的 `batch_merged` 和 `merge_status=merged` 表示已进入 main；
`release_status=pending/failed/published` 单独表示发布进度。
`pr-queue status` 会读回发布状态；后继发布包含该提交时显示 covered。
旧 `batch_delivered` 仅兼容历史记录，不再作为新合并完成条件。
发布失败不会回退 main 或覆盖上一可用包；GitHub 的 `Plugin release` 状态和
`release-blocker` 工单保存源码、失败运行及上一可用版本，相关已合并 PR 收到作者反馈。
已归档的作者会话不会因此自动复活，作者应从工单启动独立修复任务。
真实故障未恢复时，推广只接受提交消息使用 `Release-Fix: #工单编号` 的修复。
此标记不会在合并时提前关闭工单。基础设施问题记录阶段和原因；
确认为门禁遗漏时给工单加 `merge-gate-gap` 标签，必须包含对应合并前回归。
独立审阅仍负责确认回归确实覆盖故障；成功发布后关闭已被新源码覆盖的故障工单。

工作流手动入口支持发布前故障注入及短暂 hold，仅用于队列/失败演练。
故障注入工单明确标注，不对原作者派发虚假故障，也不阻塞正常合并。
hold 只是推迟真实发布；其间发现的真实构建或启动失败仍按正常故障反馈。
安装、重载及人工验收继续单独安排。
当前两线程实测与历史串行原因见 `context/results/test-parallelism-20261116.md`。
随后从 Release 读回实际包，使用既有原生 fixture、私有目录和随机回环端口，
检查包内启动器的 MCP 握手、界面资源、HTTP 服务身份及依赖就绪，关闭本次全部进程。
失败、跳过、身份错误、清理失败或报告与退出码不一致均拒绝候选。
缓存只复用依赖和编译产物，不复用其他源码的成功记录。
失败重跑使用 Actions 的失败任务重试及已有 Release 包，不重建已确认的平台包。
主线推送不再次触发整套构建；主线只接收已验证候选的同一提交。

仅更新 `context/` 内普通 Markdown、JSON 和 YAML 记录时，允许记录专用门禁。
工作流先确认主线为祖先，全部非记录文件的 Git 树与主线完全相同，
再确认该主线头具有 Actions 的成功 `Candidate gate`，执行项目检查与上下文检查。
该路径保留当前不可变插件包的原始源码身份，不升版、不构建、不重新发布。
任何代码、测试、检查器、工作流、版本或其他路径变化均走双平台候选门禁，
再按上述保守范围选择测试，不能进入记录专用门禁。
汇总门禁要求分类及所选验证路径实际成功，路径失败或意外跳过均阻止主线更新。
记录同步须正常快进，推送前再次确认主线仍为检查报告中的基线。

协调者在候选的干净检出中执行：

```bash
./scripts/promote --candidate CANDIDATE_SHA --base EXPECTED_MAIN_SHA \
  --run ACTIONS_RUN_ID --repository OWNER/REPO --output /tmp/promotion.json
```

入口检查正确仓库和工作流、分类及四项候选任务各自成功、双平台源码身份、报告和日志摘要，
重新计算范围和完整清单，核对双平台包启动报告，并从不可变 Release 下载实际插件包。
包内源码、指纹、版本、目标和二进制摘要必须与启动报告相同。
验证记录及实际包各下载一次并保留在回执旁，再核对主线未前进，正常快进推送并读回确认。
不允许强推或用跳过状态提升。
GitHub 默认使用已有 `gh` 登录；自动环境可用 `CODEX_GITHUB_COMMAND` 指定参数数组形式的
既有凭据入口，不在脚本或记录内存放令牌。

服务端主线保护要求 `Candidate gate` 成功、分支为最新，并禁止强推及删除。
仓库权限不足以配置时必须明确报告保护未生效，不能把本地脚本等同服务端保护。
合并计时从开始处理固定 PR 头，到主线确认同一候选且上述不可变包可用为止。
调查、规则开发和计时结束后的记录收尾分别列出，不混入合并时间。
以后部署使用候选渠道中同一源码身份的包，客户端加载和功能验收单独计时。

干净候选冻结后，可以一次执行推送、等待、下载核验及主线更新：

```bash
./scripts/integrate --base FIXED_MAIN_SHA --repository OWNER/REPO \
  --started-at MERGE_START_ISO_TIME --output /tmp/new-integration
./scripts/integrate --resume --output /tmp/new-integration
```

入口复用 `promote`，不中途移交人工轮询，不安装客户端。
默认从入口启动计时；提供合并开始时刻时，准备候选的时间也计入。
中断后恢复同一记录，要求同一干净候选和分支，不重置时钟或覆盖失败。
失败的 CI 不会被自动当作成功；修复源码后重新冻结新候选。
记录同步及分支清理单列耗时，不混入核心合并时间。

收尾直接在已经提升的候选工作树完成本任务卡、STATE 和 journal 的一次记录事务，
只提交一批 context 记录，避免先把候选合回协调树再重复提交。
随后仍调用 `integrate`，它自动识别 context-only，复用记录专用 CI、下载准确头报告、
核对实现未变及主线未前进后正常快进，不再次构建插件或改变原包来源。
失败继续在同一个输出目录 `--resume`；主线已前进时停止，重新整理记录。
作者监控收尾复用 `pr-queue closeout`，见 `Docs/PR-QUEUE.md`。
