# PR 交付前检查

开发提交继续只执行暂存快检，允许功能尚未完成。准备交付 PR 时，在最终代码的干净提交上运行：

```bash
./scripts/validate --scope pr --base FIXED_MAIN_SHA \
  --expect-head PR_HEAD_SHA --output /tmp/unique-pr-delivery
```

基线和 PR 头都解析为固定提交。报告保存实际源码、Git tree、实现指纹、平台、
检查器来源和比较的 merge-base。开始时拒绝脏工作区，结束时再次核对源码与检查器。
输出必须是源码外的新目录，失败、中断和重试不覆盖旧记录。总预算为 1800 秒。
PR 工作流明确检出事件中的 PR head，以事件中的 base SHA 比较，不冒称检查了临时合并提交。

## 自动选择

所有 PR 都执行项目检查、全目标 Clippy、源码包预检，以及严格核对清单的相关测试。
先收集全部 Rust 与 Python 用例并与绑定核对，再执行所选组。结果保存 inventory、
selected、not_run、逐项状态和分组耗时，缺项、重复、skip、ignored、非零退出均不能通过。
未执行项不记作通过。普通业务变化不重复执行提交规则工具自测。
按风险需要的实际包检查在长回归之前执行，先反馈启动链或连接归属错误。
实际包失败时保留原始报告，尚未运行的回归不记为通过；修复后重新交付检查。

| 改动 | 追加检查 |
| --- | --- |
| 已知界面文件 | 库、状态、存储、插件与界面相关组 |
| Rust 业务及其测试 | 全部业务组及 Python 回归 |
| 连接层、配置、原生写入、共享启动或 fixture | 实际本机临时包和连接失败场景 |
| 打包、包启动验证、服务入口或 MCP | 实际本机临时包和启动失败场景 |
| 检查工具、工作流、依赖或未知路径 | 完整测试组与实际包检查 |
| 普通上下文与说明记录 | Python 回归，仍核对完整清单 |

作者可用 `--risk connection`、`--risk package` 或 `--risk lifecycle` 追加场景，
不能取消自动选择。生命周期边界包含连接、发送、慢流接收和子进程晚退出，
复用现有模拟时钟回归。连接来源与项目零写入继续复用连接层及原生业务回归；
普通业务统一使用 App::connection，无须自行挑选客户端后台。

## 实际包

复用 package_plugin 构建当前源码的本机包，归档后实际解包，运行已有
verify_package_startup.verify，不升版、不发布、不安装或重载日用插件。
fixture 由本次源码重新构建，以 Cargo 实际输出路径和摘要绑定，不能随手使用旧二进制。

复用原 PR #6 故障演练的五场景：正常启动、配置漂移、MCP 非零退出、
错误后台零字节、服务提前退出。故障场景只有在预期边界拒绝且清理确认时才算通过，
不能把任意报错当作成功。连接变化另通过实际 HTTP 状态操作检查错误侧栏零字节及状态不变。
场景记录明确区分“检查通过”和“故障注入中的启动被拒绝”。
源码、版本、实现指纹、目标、二进制、fixture、验证器和归档摘要随报告保存。

## 交付与边界

作者在 PR 中登记原会话 UUID、主机、独立工作树及前置 PR，方便原会话接收修复反馈。
提交最终头对应的代码审阅结论，注明审阅者及被审阅 SHA；作者自述不代替独立审阅。
PR 附上 VALIDATION.json、TESTS.json 及原始日志位置，说明相关检查结果和缺少的平台。
代码变化后补跑受影响检查并更新源码绑定，不能沿用旧提交的成功记录。
本机检查只证明报告中的平台；Linux PR 工作流不代签 macOS。
该检查不包含最终多 PR 组合、不可变渠道发布或真实客户端验收，release_ready 保持 false。
协调者仍对最终组合运行既有双平台门禁、隔离启动与主线提升。

合并过程中出现失败，协调者在 PR 保存主线、PR 头、组合来源、复现命令和原始日志，
并向登记的原会话派单。会话繁忙时等待；连接失败、没有回执或作者表示受阻都不能算修复。
历史演练明确标注原 PR 与独立修复分支，不改写已经合并的原分支。
作者只在获准的修复工作树改动，保留原 PR 的祖先关系，交回新 SHA 和对应检查记录。
新头需重新审阅、重新验证，不能沿用旧头的通过记录。
协调者负责核对证据和重新入队，业务意图及冲突取舍留给作者与独立审阅者。
