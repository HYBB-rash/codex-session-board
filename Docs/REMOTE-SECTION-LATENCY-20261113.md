# 远程原生分区耗时调查：2026-11-13

已定位并在真实 Linux 客户端复现一种与历史现象一致的延迟：远程移动已经完成，
桌面内存也知道新分区，但供看板读取的分区映射尚未写入状态文件。
共享的原子状态保存采用 500 毫秒防抖，其他原子状态更新会重新计时，没有最大等待时间。
因此，等待文件中的映射出现可能用掉几秒；不能据此推断远端移动本身用了几秒。

本轮只调查和运行专用实验，没有恢复远程分区同步，没有修改或部署业务实现。
原始数据和可重跑实验脚本位于 `outputs/remote-section-latency-20261113/`。

## 具体调用链

1. 工具处理函数 `tX` 解析目标主机，再等待 `WrLE.X6`。
   副本 `renderer-tools.formatted.js:1774`、`:1844`、`:1945`、`:12225`。
   传入明确 `hostId` 时先读该主机；没有明确主机时可能跨已连接主机查找。
2. 已有远程实际分区时，调用 `setThreadSection`，最终发送 `thread/section/move`。
   新建映射时，前端 `jVb3.x` 先调用 `createSection`，后端创建实际分区并移动会话，
   然后前端把 `hostSectionIds[host]` 写回原子状态。
   副本 `renderer-739301.formatted.js:409452`、`:409537`，
   `main-615.formatted.js:110329`、`:110438`。
3. 原生引擎 `76305.Y9` 的 `setThreadSection` 等待移动 RPC，未包含固定五秒等待。
   源码还会在某些指定顺序的跨分区移动中先移入再排序，失败时可能回滚。
   副本 `main-bootstrap.formatted.js:3985`。
4. 全局状态类 `eR` 的 `set` 调用 `persistForKey`。当键是原子状态 `E.Oq`，
   保存进入 `persistDebounced`，而不是立即写文件。
   构造器设置 500 毫秒延迟；共享防抖函数 `t7` 每次调用先取消旧计时器。
   没有 `maxWait`，也没有在此次映射更新后强制 `flush`。
   副本 `main-133.formatted.js:2335`、`:2677`、`:2782`，
   `main-bootstrap.formatted.js:8285`。
5. 看板 `Catalog::load` 读取原生目录和磁盘上的 `.codex-global-state.json`，
   用映射把实际分区 ID 转成逻辑分区 ID。`confirm_move` 每 50 毫秒重读，
   但其循环期限是 `min(rpc_timeout_seconds, 4)` 秒；单次读取另受 RPC 期限约束。
   映射保存被不断推迟时，可以出现“远端成功、看板在确认期限内仍无法确认”。
   见 `src/native_sections/direct.rs:36`、`:167`、`:195`。

## 真实远程实验

`probe.py` 创建专用空会话和专用分区，不发送首轮消息、不运行模型任务。
移动工具从 Linux 真实侧栏 socket 调用，明确目标为 M1。
每次确认同时检查 Linux 磁盘映射和 M1 原生 `thread/read` 的实际位置。
确认耗时包含实验控制用 SSH 往返和轮询，不等于用户界面的绘制耗时。

正常条件，数据见 `live-move.json`：

| 操作 | Linux 工具回执 | 映射和原生位置均确认 |
| --- | ---: | ---: |
| 首次进入新远程实际分区 | 375 ms | 942 ms |
| 第二张会话进入已有映射 | 360 ms | 398 ms |
| 首次进入另一个新远程实际分区 | 203 ms | 734 ms |
| 返回已有映射 | 226 ms | 250 ms |
| 再次进入已有映射 | 155 ms | 191 ms |

本轮普通条件没有复现五秒移动。首次创建映射的额外约半秒与保存防抖相符。

随后做一次受控干扰，数据见 `live-stress.json`：

- 一次远程移动的工具回执为 **230 ms**。
- 回执后立即直读 M1，原生位置已是新实际分区；这次读取用了 **8.9 ms**。
  同时读取 Linux 状态文件，目标的 `hostSectionIds` 仍不存在。
- 持续约 4.8 秒改名另一个无会话、无远程映射的专用分区，共 36 次。
  这些更新触及同一原子状态保存计时器，不需要重放目标会话的移动。
- 到请求开始后 **5,156 ms**，磁盘映射仍未出现；停止更新后，
  在 **5,689 ms** 确认映射出现。

这在真实日用客户端上区分了“移动已完成”和“共享状态文件尚未保存”，
并验证其他分区更新能够延迟目标映射落盘。它不是等待动画或网络限速模拟。

## 原生接口与隔离源码实验

`backend-probe.py` 在 Fedora 的独立 `CODEX_HOME` 下启动同一个安装包的 app-server，
仅创建本实验的空会话和两个分区。结束后停止该进程并删除自己的缓存目录。
它排除了桌面前端、SSH 和日用数据规模，只衡量当前二进制的原生接口。

| 接口 | 样本数 | 中位耗时 | 范围 |
| --- | ---: | ---: | ---: |
| `threadSection/create` | 2 | 0.47 ms | 0.22–0.72 ms |
| `thread/section/move` | 10 | 0.84 ms | 0.52–34.32 ms |
| `thread/read`，无 turns | 10 | 0.55 ms | 0.29–1.02 ms |
| `threadSection/list` | 10 | 0.21 ms | 0.11–0.33 ms |

数据见 `backend-results.json`。这组结果不能替代真实远程时延，但能排除该接口
在空数据条件下存在固定五秒等待的猜测。

`persistence-probe.mjs` 从本次实际资源中抽取完整 `eR` 类和原样 `t7` 函数，
用独立对象和文件写入替身测试保存调度；不实例化 Electron，不修改正式状态。
无其他更新时 505 ms 保存；每 100 ms 更新一次、共 48 次时 5,414 ms 保存；
显式 `flush` 时 1.1 ms 保存。数据见 `persistence-results.json`。
这里验证的是源码调度行为，不用于估算正式磁盘写入速度。

另有一次只读 `list_threads(limit=1)` 观测：首次 5,318 ms，后两次 88 ms、22 ms。
该接口会聚合多来源和已连接主机，首次准备或缓存可能另有耗时。
没有本轮逐请求跟踪，不能把这 5.3 秒全部归于上述保存防抖。

## 结论和后续边界

历史记录 `context/journal/2026-11-08-remote-first-input.md:11` 的“约 5.2 秒、回执早于映射落盘”，
与本轮实际复现一致。旧记录没有逐阶段跟踪，不能断言当时恰好由同一种并发更新触发。
现在可以确认：把防抖保存的文件当成移动完成回执，本身就会制造几秒等待和确认超时。

后续设计应让移动回执、原生实际位置和逻辑映射的提交形成明确契约，
避免仅靠反复读取状态文件来判断刚完成的移动。单纯延长四秒期限不能给出可靠上限。
已有映射的移动较快；批量迁移已有会话时应复用每个主机、每个逻辑分区的映射。
远程连接可用性、旧客户端能力、无映射的离线主机仍需单独处理，不能只改一个开关。

清理已核对：三张新建空测试会话均已归档；三个远程实际测试分区和四个逻辑测试分区
均已删除；Linux 保留原来的五个状态分区，隔离缓存目录已删除。
没有改动普通会话的位置、连接偏好、正式配置或插件。
本次未实现功能修复，不签收完整 31 条目标环境验收，沿用既有待验证状态。
