# 五状态与原生分区一致性可行性调查

调查日期：2026-11-11，Asia/Shanghai。调查者：本会话主代理及两名只读子代理。
范围：正式看板按五状态工作，Agent 修改业务状态时，页面、原生映射、配置和发布验证同步覆盖。
本次只调查、读取和记录，没有修改业务实现、正式配置、原生分区或会话，没有部署。

## 结论

能做，不需要改变 Rust 服务、SQLite、快照 API、MCP/网页入口和原生权威状态的架构骨架。
需要局部修正状态集合的使用边界，补齐配置迁移和发布检查。
单独删除正式配置中的 completed 可以解除本次目录读取故障，但不能交付“以后改状态都不漏改”的完整需求。

“一致”应定义为：固定业务状态由代码定义；各环境绑定具体账号、主机和分区 ID；页面由后端状态清单生成；迁移和发布检查拒绝不一致的候选。
原生分区仍决定会话当前位置，业务状态清单不因此改由侧栏自动推断。
用户删除必需分区时应报告缺失，不能据此自动删除业务列，也不能按同名重建或猜测账号。
任意增删自定义状态、让原生侧栏随时决定看板有哪些列，不属于这次五状态一致性修正。

“每次 Agent 修改都一起正确修改”可以落实为共用定义、明确迁移和必经验证。
它不能成为对任意 Agent 绕过发布入口、用户检查后继续改分区、外部系统崩溃的无条件保证。

## 为什么漏改

1. `src/model.rs:3` 保留六状态历史词汇，`states_for(false)` 提供日常五状态，`board_state()` 兼容旧 completed 输入。
2. `src/config.rs:174` 允许配置包含六种已知键，只强制五项完整、UUID 合法及不重复。配置测试明确允许六项和五项两种输入。
3. `src/native_sections/direct.rs:39` 却要求某账号包含配置中的全部分区；`:82` 又验证全部配置项。
4. 因此一条允许保留的旧配置，被读取路径变成了所有原生读取的必需前提。聚合读取的 `src/native_sections.rs:58` 也遍历全部配置。
5. 零候选和多候选共用一条错误，隐藏了真正缺失项。

历史核对发现，2c65c66 引入五状态显示并允许保留旧映射；ab2a7b8 引入 direct 路径；
3d15368 增加显式六状态兼容模式。保留冻结兼容模式有必要，但不要求日常原生模式保留第六分区。
现存多个版本配置内容相同并持续含六映射，这只能证明当前文件，不能证明各次历史时刻文件从未改变。

v0.2.38 的 native5 与 remote 有效验收配置实际也含 completed。
N5-STATE 覆盖五列、五状态操作和兼容输入投影，没有覆盖“原生第六分区已不存在”。
`scripts/verify_remote_release.py:175` 检查模式和配置/二进制身份，但没有要求 native5 映射恰好是有效五项。
`scripts/build-plugin:5` 不消费完整验收报告，提交钩子也不执行完整外部汇总。
v0.2.73 部署记录 `context/tasks/completed/deploy-no-record.md` 明确未做完整外部签收，没有宣称 release_ready。
不能把这次问题解释为冻结六状态契约强迫保留原生 completed，也不能声称旧报告已验证删除后的行为。

## 当前骨架是否足够

| 层 | 已有能力 | 所需调整 |
| --- | --- | --- |
| 模型 | 状态标识、中文名、顺序已有共同定义；区分日常与兼容模式 | 对外提供统一的日常状态与有效绑定访问方式 |
| 页面 | 列、顶部导航、选择器均遍历后端 states；排序也派生于模型 | 无须再加一份前端状态数组；补跨层断言 |
| 原生适配 | 逻辑分区到 hostSectionIds，再到后端目录；读回确认已有 | 账号筛选、目录校验、观察和移动都消费同一有效绑定集合 |
| 数据 | 备注、人工确认、历史、原生位置缓存已有独立存储 | 单纯退役分区绑定不需要新库或整库迁移 |
| 配置与发布 | 配置独立、configId、构建哈希和服务身份核验已有 | 补显式退役映射迁移，以及实际候选配置与目录预检 |
| 验收 | 冻结六状态与日常五状态分开，同源码/二进制汇总已有 | 增加缺失第六分区的必测场景；发布入口消费结果 |

管理上缺的是把“业务状态变更”作为一个包含配置迁移和部署核对的完整变更。
技术上缺的是一个一致的有效状态集合，而非新的服务、消息总线、通用状态机或分布式配置中心。
部署 UUID 是环境数据，不应搬进源码；既有六状态表、旧标题前缀识别和执行协议也不能全仓删掉 completed。

## 推荐的最小方案

1. 沿用 `model::states_for(false)`，派生日常状态和 `(state, label, logical_id)` 有效绑定，避免另写五状态名单。
2. 原生模式要求配置键集合与日常状态集合一致。推荐一次显式配置迁移移除退役 completed，保留备份与变更预览；未迁移时明确报告退役键。
3. 读取、账号解析、目录校验、移动目标、受管理分区判断使用同一有效绑定。已知旧输入的兼容规则单独保留，不让旧输入重新扩大原生依赖集合。
4. 将错误区分为缺少必需分区、退役映射、无匹配账号、多账号歧义、缺少主机映射、名称变化等，并给出状态名及恢复步骤。
5. 复用现有构建、服务身份核验与验收工具，增加必经发布预检。对实际候选配置、唯一账号、五项 ID、名称、local 映射、真实目录、二进制和 MCP/HTTP 指向逐项核验。
6. 以同一候选源码和二进制补齐五状态回归及目标客户端验收，再明确切换服务及插件。配置变化改变 configId，不把修改文件当作已运行生效。

对比方案：仅删现场 completed 映射能处理当前故障，但不能防止复发；放宽为任意一项匹配或取首个账号有写错目标风险；引入通用动态状态系统超出当前需求。
“加载时规范化并提示退役项”也可实现，但本次推荐显式迁移，避免磁盘原配置、运行有效配置和发布收据长期不一致。
本次没有实施上述任一方案。

## 边界情况与提前约定

| 情况 | 必须满足的行为或限制 |
| --- | --- |
| 用户再次删除五个必需分区之一 | 明确指出缺哪一项，保留卡片和备注，阻止不确定写入；不自动删列或重建 |
| 删除后创建同名分区 | ID 已变，不能仅按名称自动认领；需要显式重新绑定并核验主机 |
| 多账号或账号切换 | 保持唯一匹配要求；身份变化后重新核验，不能取第一个或跨账号拼齐五项 |
| 重复 UUID、错误 UUID、同名不同 ID | 在候选配置和目录阶段拒绝；不能只检查数量等于五 |
| local 与 remote 主机映射差异 | 按目标主机核验；当前远程实例构造会设置 native_sections=false，本机目录成功不代表远端侧栏已同步 |
| Pinned、未分区及其他自定义分区 | 保留当前位置和既有保护，不能为凑齐五列批量移动；未映射位置的 unknown 展示不等于获得移动授权 |
| 用户把必需分区改名 | 当前中文名严格匹配；产品更名要同时迁移名称约束，避免只更新网页 |
| 旧 completed 数据与标题 | 保留历史、备注及审计；日常投影和旧前缀清理继续兼容，不能误删执行协议的 completed |
| 恢复后自动归档重新可用 | 本机当前开启半小时归档；迁移前审阅新鲜待归档位置、人工确认和新输入，避免把修复当作新的归档授权 |
| 迁移与重启中断 | 分步预检、备份、显式发布；失败保留原配置；跨进程恢复需重新核验，不能承诺外部事务回滚 |
| 旧 MCP、旧页面及多入口 | 核对实际版本/configId，处理已过期编辑；旧会话可能仍绑定旧实例，修改源码或磁盘文件不等于全部入口切换 |
| 客户端文件正在写入或格式改变 | 解析失败保留旧缓存并报告；不能回退成空目录或猜测 ID |
| 检查后用户再次移动或删分区 | 运行时继续校验；外部接口没有位置 CAS，不能消除检查到写入之间的竞争或 ABA |
| socket、远端握手等独立故障 | 单独报告，不能把去掉退役映射当作这些故障也已解决 |

只读 SQL 还发现本机保留有未归档 completed 人工记录，以及两条 native_state 为 to_archive 的未归档缓存。
这些计数不证明新鲜原生位置或归档资格；不能直接批量改写、补归档或据此判断会话丢失。
当前根库标题队列为空，部分远端仍有标题队列；迁移不应盲目重放旧状态写入。

## 实施验收与剩余不确定性

新增自动覆盖应包括：完整五项配置穿过实际读取链路、退役第六分区完全不存在、旧六项配置按迁移策略处理、

页面列、导航、选择器、排序、更新接口和原生绑定必须核对同一状态集合；不能只证明五列显示。
冻结 31 条、独立参考模型和锁保持不变，在 N5-STATE/N5-RECOVERY 等扩展验收中增加覆盖。
真实客户端需验证读回、手工跨列、自动执行阶段、备注保留、刷新重启、过期提交和受控归档。
完整发布仍要求基础完整验收和原生/远程汇总证据绑定相同候选源码、二进制与实际配置。

已消除的关键不确定性：零候选的直接原因、五项真实目录是否存在、源码与正式配置的差异、漏测来源、是否需要架构重构。
实施后才可消除的部分：候选版本在真实客户端的完整操作闭环、多入口实际切换、独立远端故障恢复、启用归档后的行为。
本次目录只读成功没有代签这些项目，也没有新的 release_ready=true 结论。
