## 完整验收的判定

合并阶段以最终组合自动回归通过、主线更新及可运行插件包产出为完成条件，
见 `Docs/INTEGRATION.md`。下面的完整验收属于独立阶段，不阻塞符合条件的合并。
验收阶段如何组织及记录留待后续研究；31 条契约及真实环境证据要求继续保留。

在项目根目录执行：

```bash
python3 scripts/verify_acceptance.py --scope automated --report /path/to/automatic.json
python3 scripts/verify_acceptance.py --evidence /path/to/evidence.json --report /path/to/final.json
./scripts/check
```

第一条只检查自动部分，不能单独作为“完整验收完成”的结论。第二条默认检查完整验收。
只有每条需求通过、`release_ready=true` 且退出码为 0，才达到这份契约的完成条件。
有失败返回 1；自动部分通过但外部验收缺证时返回 2。跳过、预期失败、零测试、
缺少绑定、缺少结果和测试收集错误都不能记为通过。

适配器会核对实际收集的完整测试集合，防止绑定漏掉回归测试。新增测试后应将它
绑定到对应需求。报告保留逐需求结果、逐测试结果、需求 SHA256 和实现指纹。
实现指纹覆盖代码、测试、规范、清单、依赖锁及离线资产，不包含运行数据和项目日志。
报告应保存在源码之外。验证器拒绝报告覆盖规范、实现输入、证据及其附件，
也拒绝在参与指纹的目录中生成报告。

`contract.lock.json` 固定需求文件和独立参考模型。不得为了消除失败而降低要求、
删除断言、跳过用例或重新生成锁。需求确需变化时，先列出差异交用户确认。
指纹和锁用于防止误用旧结果，不能证明执行者提供的证据真实，也不能防御执行者
同时篡改验证器和证据。因此迁移评审仍应检查测试和证据内容。

## 状态流转定义

自动事件只产生进行中、已阻塞、待审阅。其他状态由人工选择；人工也可选择这三个状态。
“待归档，然后已完成”规定显示和常见收尾顺序，不要求逐列经过。
进入待归档不执行真实归档。正常答复结束表示本轮等待用户审阅，不代表任务已验收。

| 观察到的证据 | 结果 |
| --- | --- |
| 当前轮次实际开始或恢复执行 | 进行中 |
| 当前执行等待批准或明确交互工具输入 | 已阻塞 |
| 当前轮次失败、中断或运行系统异常 | 已阻塞 |
| 当前轮次正常结束 | 待审阅 |
| 同一执行阶段的重复快照 | 保持，包括人工选择 |
| 只查看、助手正文声称完成、尚未执行的新输入 | 不单独触发自动状态 |
| 历史读取失败或运行观察连接错误 | 保留状态并报告读取异常 |

首次启用时的旧人工选择和旧失败记录有独立保护。新用户输入的复核提示与执行状态分开。
标题同步在状态成功保存后立即尝试；失败补偿才使用后台重试，不混淆二者的触发时机。

## 有限模型验证的范围

`model.py` 不导入业务实现。它独立表达人工选择、已观察执行阶段去重和新阶段覆盖规则。
测试遍历 40 个可达抽象状态，每个状态检查 13 个动作，共 520 条单步转换，
然后用真实 `Store` 重放代表路径并比较状态、人工标志、备注及版本。

动作包括六种人工选择、运行、审批等待、输入等待、系统异常、正常结束、查看和重启。
每个用例从已经观察到运行阶段的单个轮次开始，时间单调前进；版本按增量比较，
探索时不把版本绝对值作为新状态。失败和中断另有运行证据表和回归用例。
首次观察、不同轮次、新输入、标题并发及服务接线由其他测试或外部验收负责。

这是有限抽象范围内的穷举一致性检查和可执行验收，不是对整个插件的数学证明。
它不证明任意线程调度、操作系统崩溃、真实网络及 UI 均正确，也不保证轮询捕获
两次采样之间的每个短暂阶段。若将来要求逐事件无遗漏，需要增加需求并实现事件订阅。

## 外部验收步骤

这里的“外部”表示在独立运行的实现上取证。界面项目必须使用目标 Codex 客户端；
服务补偿可用隔离的受控集成环境。普通函数测试或检查 HTML 字符串不能替代它们。
测试会话使用用户提供或明确授权创建的专用会话，不在实际工作会话上制造故障。

| 编号 | 操作和必需证据 |
| --- | --- |
| STATE-001 | 在目标客户端分别展示六列、导航及选择器；记录三个实际顺序和空列。 |
| AUTO-001 | 记录专用会话 ID，发送输入使其真实执行，随后验证暂停后的实际恢复。记录运行证据与看板前后状态，批准本身不得抢先改状态。 |
| AUTO-002 | 在受控会话分别验证审批、交互等待、失败或中断、系统异常，以及仍在重试而未暂停的请求错误；记录原始执行证据、自动原因和人工备注。 |
| AUTO-003 | 让专用轮次正常结束，独立读回待审阅；包含普通澄清答复，确认没有自动进入两个收尾状态。 |
| TITLE-001 | 通过正在运行的 HTTP 和 MCP 保存及运行观察触发改名，独立读回完整原生标题；手动先改长正文，确认使用最新名称。 |
| TITLE-003 | 独立启动主程序，令标题端点失败后保存状态；核对提示及数据库，重启再恢复端点，不手动调用 sync，确认主程序后台完成补偿。 |
| DISCOVERY-001 | 在目标环境预置已知交互会话 ID，完成扫描；新增专用会话后重新发现，核对 ID、范围、去重和分页完成标志。 |
| NAV-001 | 准备两个同名但 ID 不同的会话，分别点击并核对实际客户端和原会话 ID；从标题拖动不跳转，不增加消息或执行轮次。 |
| APP-001 | 从插件安装缓存加载，点击最左侧窄栏图标；载入会话，在备用网页与原生入口间核对同一记录。 |
| UI-001 | 在原生 MCP 容器实际拖卡片和标题跨列并刷新，核对备注；同列及列外不写入；窄窗口验证横向及边缘滚动。 |
| UI-002 | 在原生容器拖入阻塞列，依次取消、空原因保存、有效原因保存；记录状态和备注的前后结果。 |
| UI-003 | 搜索标题与项目，验证空目标列；键盘操作表单；拖动和编辑时让刷新到达，确认输入、滚动位置和卡片稳定。 |
| HEALTH-001 | 对隔离实例依次注入扫描失败、部分历史失败、运行断连、标题失败及未完成分页；记录界面提示和旧状态保留。 |
| DELIVERY-001 | 解包到新目录，执行自动验收及上下文检查，核对资产与 PACKAGE-MANIFEST.json 的哈希；记录目录、命令、退出码及输出。 |

`evidence.example.json` 是未通过的空模板。复制到源码目录之外，为以上每项记录
执行者、环境、带时区的时间、实际结果说明和附件路径及 SHA256。
顶层两个指纹从本轮报告复制。附件路径相对证据文件，可指向截图、交互录像、
受控协议日志或独立读回记录。代码变更后应重新取证。

验证器只核对证据字段、文件存在、哈希及版本，不会看一张截图就自动证明交互正确。
人工或具备真实操作能力的 Agent 应逐项审阅证据内容，不能用占位文字签收。

## 测试适配器协议

验证器按 `bindings.json` 的参数数组启动适配器，不使用 Shell 拼接。
适配器在项目根目录运行，标准输入是一行 JSON：

```json
{"protocol":1,"tests":["完整的测试标识"]}
```

标准输出只返回一个 JSON 对象，日志写标准错误：

```json
{"protocol":1,"results":[{"id":"完整的测试标识","status":"pass","detail":""}]}
```

允许的结果是 pass、fail、error、skip，只有 pass 通过。所有请求的 ID 必须各返回一次，
缺少、多出、重复或适配器非零退出均拒绝通过。当前适配器
`scripts/rust_adapter.py` 按目标目录实际构建 Rust 测试二进制，核对完整测试清单，
运行并收集逐项结果，再合并标准库 unittest 对独立验收器的测试。
Rust 状态测试读取冻结的 Python 参考模型，在真实 Rust Store 上重放 520 条转换。
原型的业务测试已改写为 Rust。原始 Python 源码和测试保留在基线压缩包供追溯。
适配器按目标工作目录收集和导入测试，即使适配器脚本从另一个目录启动，
也不能因此改测脚本所在的旧项目。

研究与选型采用现有 unittest 的结果机制，增加独立状态模型及严格完成门槛，
不引入运行时测试框架依赖。参考标准库文档：

```text
https://docs.python.org/3/library/unittest.html
```
