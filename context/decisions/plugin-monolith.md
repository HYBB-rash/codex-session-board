# 插件是单体，不启动后台

## 决定

插件进程就是看板。它跟随 CodeHost（拉起这个插件的 Codex 进程）启动和退出。脱离插件的服务进程不由插件拉起。

会话状态留在数据库里。会话控制的形式化模型不包含进程寿命。

## 理由

看板原先由插件调用 `service::launch`，再把 `serve` 放进新的进程组。CodeHost 关掉或重载插件之后，那个进程还在。Codex 安装器会把插件缓存目录整棵换掉，启动记录里的程序路径就对不上，侧栏拒绝读取。

没有用户需求要求 CodeHost 退出后看板继续扫描或自动归档。本机执行状态来自 Codex 自己的连接。桌面不在时，后台也看不到新的执行。

## 未采纳的做法

把这条限制写进 `AGENTS.md`。那只在读过规则的人遵守时才生效。

只在 `build.rs` 里搜索 `service::launch` 这几个字，同时把 `main.rs` 整份放行。插件入口仍和启动函数在同一个编译单元里，换个写法就能编过。

## 后果

`service::open` 是唯一的打开方式。匹配的数据目录、配置和构建已经在运行时，调用方直接使用它。否则当前进程自己监听。`serve` 和插件的 `mcp` 都走这里。没有子进程，也没有 `launch` 子命令。

看板不读写 `server.json`。复用和停止都问配置里的端口。`/api/info` 对得上数据目录、配置和构建，就用那一份。数据目录锁被占用而端口没有响应时，不另起一份，也不把停止说成已经成功。停止核对 HTTP 报出的 PID 和该进程的启动时间，用 pidfd 发信号，等到进程实际退出。不比较程序路径、设备号和 inode。

`build.rs` 拒绝源码里再出现 `managed_launch`、`.arg("serve")`、用当前程序拉起子进程、`rpc/capture.rs` 以外的 `process_group(0)`，以及生产代码里的 `server.json`。插件入口仍然只能是 `mcp::serve`。
