# 会话看板归档状态与交互设计调研

**建议采用「可找回的归档结果」。** 归档仍是一键提交。看板服务先保存本批六条的名单，再逐条处理。回执不明时，先显示「正在核对」，其余条目继续。用户可以关掉看板，重开后仍从「归档结果」找到逐条结论。这个入口在卡片随原生活动列表消失后仍可用，也是页面内核对方案缺少的一步。

首版建议保留近期批次和仍待核对的批次，做到隔天可找回。样稿把「关闭看板」理解为离开界面。已接收的批次在看板服务仍运行时继续提交，服务中断后只核对已经尝试过的项，待提交项由用户重新决定。若实际用户愿意等到本批发送完再离开，可以保留持久结果，省掉服务端接管逐条提交。若现场测试发现关闭面板同时终止看板服务，首版采用这项较窄的承诺，直到验证有独立生命周期。若盲测中用户普遍找不到「归档结果」，优先更改入口位置和命名，再决定是否扩展历史。

## 候选比较

决定用户行为的分歧是「结果跟着当前页面，还是能从一个独立入口找回」。下列决定次数从点击「归档 6 条」后计，导航与查阅单独说明。两秒为本案发生的时长和样稿的演练间隔，其他批次的核对时间由原生端及分页决定。

| 方案 | 此刻要等多久、要作几次决定 | 关闭和重开 | 接口能支持的承诺 |
| --- | --- | --- | --- |
| 现有看板 | 约 7 秒后见整批反馈。遇到第四项，用户自行决定去原生端找，还是从卡片再归档。刷新后甚至没有卡片入口。 | 页面结束后缺少批次记录。关闭中途可能让后续条目未提交。 | 五个成功回执可靠。HTTP 异常、本地旧行、卡片缺席分别无法证明第四项未完成、已保留和已归档。 |
| 页面内核对，沿用前次建议 | 报错立即提示「正在核对」，其余条目继续。两秒场景自动得到证据时需要零次决定。仍未知时可点一次「核对结果」。 | 该次结果由活页面持有。关掉或重新载入后，有卡片才能从会话继续找线索。页面发送循环尚未完成时，后续条目可能没送出。 | 在本页可用同一来源的原生归档列表确认当前状态。需要补只读核对入口和分阶段结果。 |
| 可找回的归档结果 | 已接收后可以离开。仍在页面时自动尝试核对。无结果时只提示可稍后重开，或选择点一次「核对结果」。隔天通过「归档结果」打开明细。 | 保存的名单、时间和结果跨刷新。同一个服务实例可以接着处理这批已接收的条目。若服务重启，已尝试项走只读核对，明确未尝试的项保留为「未提交」。 | 看板自己提供批次 ID 和状态。原生端只能证明当前归档状态、有明确版本拒绝等有限事实。等待证据的项可以长期保持「待核对」。 |

页面内方案足以消除本案的错误用词，也适合快速确认。可找回方案多保存一份记录，让「可以离开」有可复查的依据，覆盖委派书指定的隔日场景。代价是多一个导航入口、一个须约束保留期限的数据表，以及明确接受整批之后的服务生命周期。三案共用现有逐条顺序、新输入校验和原生归档边界。

## 状态与证据

| 此前 → 现在 | 达到条件 | 用户看到什么、能做什么 |
| --- | --- | --- |
| 已接收 → 等候提交 | 冻结目标清单和版本，持久化成功，尚未交给原生写请求 | 本批记录可找回。看板服务存活时继续，明确没发送的项在中断后显示「未提交」。 |
| 等候提交 → 正在归档 | 该项进入归档作用域，记录可能已经发送的边界 | 展示进度。这一项暂时禁止再次归档。 |
| 正在归档 → 已归档 | 取得本次有效原生归档回执 | 结果记完成，卡片随可见原生状态移出待归档。 |
| 正在归档 → 未归档 · 有新输入 | 本次有明确的写前拒绝，证据能证明没有发出 `thread/archive` | 明确说明有新输入。打开原会话，核对后从卡片确认新输入。后续归档是另一次授权。 |
| 正在归档 → 正在核对 → 待核对 | 传输丢回执或执行结果不明。发起一次有界读回。读失败、来源变更、列表不全、两边均缺席，或只看到当前活动 | 逐条保留「待核对」。一旦检查在途结束，可离开或点「核对结果」。活动卡片若仍可见，禁用该项归档。 |
| 正在核对或待核对 → 核对时已归档 | 同一账户、主机和数据来源的原生归档列表读到精确 UUID | 记录核对时间，显示「当前已归档」。原生结果有证据就可更新计数，本地标志同步状态单独记录。 |
| 已归档 → 后来重新可见 | 确认原生会话后来被取消归档或重新出现 | 原批次保留当时的确认结论和时间。卡片按当前原生状态显示，可注明后来变化。 |

活动列表命中只说明现在可见。旧写入可能仍在处理，也可能已经归档又被取消。一次完整的归档列表未命中同样无法证明旧写请求的结局。因此「核对结果」只执行读取，过了两秒或过了一天都保持这个语义。明确未提交的条目或执行前明确被拒绝的条目，满足当前前置条件后才允许用户发起新写入。

现有 `thread/archive` 只接收 `threadId`，无旧写请求查询或批次幂等键。`archive_checked` 先查归档列表再决定写，`verify_input` 在写前核对新输入。同一看板实例按 UUID 加锁。现有层对 HTTP 的普通 `400`、工具错误字符串和列表缺席均不能作确定的操作结论。跨重连查同一主机和账号，原生权威来源发生变化时保持待核对。 [Codex App Server](https://developers.openai.com/codex/app-server)

## 实施范围

- **看板服务。** 归档共享入口把接收、明确拒绝、原生写结果和本地标记同步分别记录。前端生成操作 ID，服务以同一来源与不可变名单去重。先提交操作记录再派发写请求，重新提交同一 ID 返回已有记录。状态查询由独立的只读入口提供。丢接收回执时先按该 ID 查，成功的和结果不明的原生写均不可盲重放。若本地库暂不可用，只有成功读回批次记录后才显示「可以离开并找回」。保存标题快照、时间、来源、UUID 和版本即可，正文与令牌留在现有存储边界。
- **界面与桥接。** HTTP 和 MCP 两种入口共用批次结果。把结果区放在看板栏，独立于卡片筛选和定时快照。只更新有证据的条目与计数，保留原批次中被拒绝的结果。实际实施验收再用键盘和读屏验证状态更新是否抢焦点。
- **可以省去的改动。** 保留官方客户端、原生写入流程、既有排序和分区。首版省去跨重启恢复写队列、定时永久追查、撤销、全量历史和外部通知中心。对重启中的批次，只读核对可能已提交的项。若接受必须等到发送结束才离开，还可省去服务端逐条调度，仅持久化发送记录和结果。
